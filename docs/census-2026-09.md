## Detector quality: two rounds of self-correction

Security tooling earns distrust when it cries wolf, so the detector is measured against real artifacts, not just unit tests.

- **v0** treated any `node -e` hook as a shell pipeline. Against the three hooks it flagged, precision on the critical tier was **0/3**: two install banners and a build step.
- **v0.1** required fetch/spawn/decode evidence and added content inspection of the script a hook references. It found a real pattern, but it also flagged **string literals**: an install notice containing a URL, and a warning message containing `curl ... | sh`. Both were false positives.
- **v0.2** splits the two cases. A `postinstall` command is matched raw, because the quoted argument of `node -e "..."` is the executed code. A referenced script is matched after strings and comments are stripped, because quoted text there is usually data. Module names (`node:https`, `require('https')`) are matched before stripping.

A hand-labeled corpus of 8 samples (4 benign artifacts taken from the false positives above, 4 malicious shapes) is asserted in the test suite: precision and recall on the critical tier are both 1.0. Eight samples is small and hand-labeled; it is a regression guard, not a benchmark.

## Notable pattern: install hooks that download and execute a binary (11 servers)

These packages publish a `postinstall` of `node scripts/install.js`. Inspecting the published script (read-only, fetched from the package registry) shows it resolves a platform archive from a GitHub release, downloads it over HTTPS, verifies a SHA-256 sidecar fetched from the **same origin**, extracts it (`tar` / `unzip` / PowerShell `Expand-Archive`) and installs the binary.

Two properties are worth recording, and neither is a vulnerability claim:

- The checksum protects against transport corruption, **not** against a compromised release origin, because the expected hash comes from the same base URL as the artifact.
- The base URL, the repository and the version are overridable through environment variables (`LABBY_RELEASE_BASE_URL`, `LABBY_REPO`, `LABBY_VERSION`). A redirected download would be validated against a checksum fetched from the same redirected location, so verification adds no protection on that path.

## Hook-level critical (1)

- `ai.etincel/etincel-nonfiction` (`etincel`): scripts.postinstall matches process-spawn: "node -e \"require('fs').existsSync('tsconfig.json')&&require('child_process').execSync('npm run build',{stdio:'inherit'})\""

This one is a build step (`execSync('npm run build')`) gated on a `tsconfig.json` that an installed tarball does not contain. It is reported because it spawns during install; it is not evidence of intent.
