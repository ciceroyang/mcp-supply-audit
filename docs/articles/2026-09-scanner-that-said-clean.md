# A scanner said "clean" while four of its scanners were dead

*ciceroyang, September 2026*

This is the story of a measurement I got wrong, a bug I found because of it, and the tool I ended up building so that bug cannot exist in my own work. Everything below is reproducible from public sources, and every number is regenerated by a workflow rather than typed by hand.

## Start with the bug

I was running AgentAuditKit 0.6.5 over some real MCP configuration when I noticed its report contradicting itself. A file with invalid UTF-8 had crashed four scanners. The summary said so:

```json
{"critical":0,"high":0,"medium":0,"low":0,"info":4,"total":4,"reported":0,"minSeverity":"low"}
```

Four crashed scanners, and `reported: 0`. A scanner failure is recorded at INFO severity, INFO is below the default reporting floor, and it is below every value `--fail-on` accepts. So the crash was not shown, and it was not fatal. `--score` still returned `100 A`. The SARIF output, which is what GitHub code scanning reads, had zero results. `--fail-on low|medium|high|critical` all exited 0. There is no `--fail-on info`, so no flag combination makes a crashed scanner fail a build. I reported it as [agent-audit-kit#743](https://github.com/sattyamjjain/agent-audit-kit/issues/743).

The failure mode has a name. The tool failed open: the security gate reported success while part of it had not run. For a scanner, that is worse than a false positive. A false positive costs attention. A false clean is a green checkmark on work nobody did.

## The measurement I got wrong

I was looking at that report because I had been measuring agent-security rule sets against their own published corpora — the ones the projects use to tune themselves. My first published number for [Agent Threat Rules](https://github.com/Agent-Threat-Rule/agent-threat-rules) was **19 of 820 benign samples flagged, 2.3%**. I posted it in their false-positive demotion PR. It was wrong.

The cause was a hand-rolled YAML line scanner. The catalogue writes regex values in double quotes, single quotes, block scalars and plain scalars. My scanner understood double quotes. It silently kept **1,128 of the 3,443 conditions** and threw away the other two thirds without failing. The corpus was also six files of a larger set.

I found out because the numbers stopped making sense: a different run over a bigger corpus gave a much higher flag rate, and two instruments disagreeing by 10x means one of them is broken. I replaced the scanner with PyYAML, and re-ran against the whole published benign corpus: **11,780 samples across 26 files**.

| semantics | rules applied | samples flagged |
| --- | --- | --- |
| pattern level, all fields | 3,443 | 4,770 (40.5%) |
| pattern level, free-text fields only | 3,282 | 1,326 (11.3%) |
| pattern level, `content` only | 1,417 | 909 (7.7%) |
| rule level (conjunctions and gates honoured) | 825 | 4,609 (39.1%) |

The gap between the first two rows is the whole story of rule-set measurement and it is easy to miss. 3,827 samples are matched by a single `tool_name` rule whose patterns include `exec|execute|run_command|shell|bash|cmd`. Feeding a document body through a pattern written for a tool *identifier* is a category error, not a false positive. A scanner that reports that as a finding, and a researcher who reports it as a false-positive rate, are both wrong.

The corpus carries its own ground truth: 353 samples name the rule they were written **not** to trigger. At rule level, **0 of the 172 testable ones fired**. The rule set separates its own benign twins perfectly. The 13 pattern-level hits were an artefact of ignoring conjunctions — for instance a rule requiring *both* a tool-invocation envelope and an `mcpServers` block, matching documentation that only had the second half.

The part I did not expect: ATR publishes its own false-positive measurement, `data/benign-fp-measurement.json`, over 13,848 samples in five input shapes. That gave me something better than agreement on a method — an independent ranking to check mine against. Ranking rules by benign pressure, my pattern-layer reimplementation agrees with their full engine at **Spearman rho 0.952 over 793 rules**. Summed by maturity, their 106 stable rules account for **7 false positives in total**; the rest sit in `test` and `experimental`, which is exactly what their demotion loop is for.

Two instruments agreeing on order, and disagreeing on magnitude for precisely the rules whose fields are structured, is a good result. It means the ranking is trustworthy and the raw counts are not, which is the honest thing to publish.

## The same method on a different tool

AgentAuditKit publishes 13 vulnerable configuration examples with expected rules. Running it against its own labels gave **73 of 73 expected rules fired**, all 13 meeting their minimum finding count. Recall, on their own terms, is complete.

The false-positive side is harder, because no benign project corpus is published. I took 37 `.mcp.json` files from 37 distinct public repositories and scanned each in isolation. **32 produced at least one finding**, and `AAK-MCP-ATTEST-001` alone fired on **30 of 37 (81%)** — a policy rule that wants a signed clearance assertion almost no real config carries. A rule that fires on four configs in five cannot separate a careless project from a careful one.

I want to be precise about what that number is not. Those configs are unlabelled, so a finding may be a genuine hardening gap in that repository. It is a measure of **discriminating power**, not a false-positive rate. Reporting it as the latter would be the same mistake I made with the YAML scanner, in a different costume.

Pointing the same corpus at a third tool produced the second finding in this series. `atr scan` takes a `.json` path, parses it, and evaluates only those records that carry a `content` field — so a `.mcp.json` is parsed, skipped, and reported as `events_scanned: 1`. A directory path is either handed to the file read (`EISDIR`) or routed to the SKILL.md collector, and the shipped GitHub Action runs the scan under `set +e`, replaces the missing output with an empty SARIF, and prints `clean`. I reported it as [agent-threat-rules#575](https://github.com/Agent-Threat-Rule/agent-threat-rules/issues/575), with the reproduction in [findings/atr-4.0.0-config-scan-noop.md](findings/atr-4.0.0-config-scan-noop.md). It is the same question as the first bug one layer out: not "was there a threat", but "was there a scan".

## So I built the tool I wanted to be measuring

[agent-guard](https://github.com/ciceroyang/agent-guard) exists because of the bug at the top of this post. It is a small static scanner for agent and MCP projects, zero runtime dependencies, nine checks: MCP configuration, install hooks, content injection, transport, tool descriptions, supply chain, agent settings, A2A agent cards, and source injection.

Its reason to exist is one invariant. Every scan ends in `clean`, `findings` or `incomplete`. `clean` is only emitted when **every** check ran to completion. A check that throws makes the scan `incomplete`, prints the failure, writes it to SARIF as its own error-level result so code scanning cannot miss it, and exits **2 — at every `--fail-on` level**. Lowering the threshold cannot turn a partial scan into a pass. The only way through is an explicit `--allow-incomplete`, and the report still says `incomplete`.

That is the shape of the bug I found, turned inside out. You cannot have a green build from a scanner that did not run.

Four things I would not have built without the measurements:

- **The injection check knows about quoting.** An override phrase inside a fenced block or an inline code span is reported at low severity with a `(quoted: ...)` marker. It is still reported. Security write-ups are made of examples, and suppressing them outright would be a blind spot; treating them as live instruction text makes the tool useless on any repository that documents the problem.
- **Coverage is reported, not assumed.** A config that exists but does not parse lands in `coverage.unparsedFiles`, not in the findings. It is a hole in what was assessed, and calling it a finding overstates what the scan knows. The same rule governs the census: of 245 resolved packages, 22 whose manifest could not be fetched are counted as unmeasured — folding them into "clean" would have made the headline 238 instead of 216, and that number would have been false.
- **The rules get measured against real data, and lose arguments.** Over 37 real-world configs, an early version of the credential rule fired five times on values like `GITHUB_PERSONAL_ACCESS_TOKEN` and `${MY_KEY}`. Those are placeholders and references, not secrets. Tightening it removed all five false positives and no true positive. Separately, every mutable-source dependency hit turned out to be a `devDependency`, which cannot reach a consumer of the package, so those now report at a lower severity with `(dev-only)` in the message. The findings stayed; their weight changed.
- **A field the scanner cannot read is reported, not defaulted.** The MCP check coerced a malformed `args` or `command` to `[]` or `""`, so `{"command": "node", "args": 42}` scanned as `clean` — the entry was never assessed and nothing said so. It is a finding now (`AG-MCP-016`), which is the same invariant one level down: a tool may not claim to have assessed what it could not read. I found it by pointing my own scanner at the corpus I had built for the other two.

The project carries a committed corpus — six benign projects that must stay silent, eleven that must fire — and CI fails on either a false positive or a missed rule. The scanner scans itself in CI, with its own intentional bad examples excluded. And it ships as a GitHub Action whose wrapper returns the CLI exit code unchanged, with a test that asserts a bad project fails: a wrapper that swallows exit code 2 would quietly undo the one guarantee that matters.

## If you are evaluating a scanner

Ask it one question: **what did you not do?** A report that lists findings but not coverage cannot answer, and the answer matters more than any individual finding, because "clean" is the highest-stakes word a security tool emits.

Then find its own test corpus and its own published numbers, and check the method rather than believing the summary. Mine was wrong for exactly as long as I did not.
