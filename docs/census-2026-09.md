## PyPI: the install-time dimension is unknown, and said so

PyPI metadata exposes no install hooks, so the audit does not borrow the npm verdict. It distinguishes what the artifacts allow:

- **35** packages publish a wheel, which unpacks without executing code — but an sdist build would not, and metadata cannot say which a given client will use, so the verdict is `unknown`, not clean.
- **0** packages ship no wheel for the declared version: installing them builds from source, which executes build code (`pypi-sdist-only`, medium).

## Detector quality: two rounds of self-correction

- **v0** treated any `node -e` hook as a shell pipeline: precision on the critical tier was **0/3** against real artifacts (two install banners, one build step).
- **v0.1** required fetch/spawn/decode evidence and inspected referenced scripts, but still flagged **string literals** (a notice containing a URL; a warning containing `curl ... | sh`).
- **v0.2** matches a `postinstall` command raw and a referenced script after stripping strings and comments, with module names matched before stripping. A hand-labeled corpus of 8 samples guards precision and recall; it is a regression guard, not a benchmark.

## Notable pattern: install hooks that download and execute a binary (11 servers)

These packages publish a `postinstall` of `node scripts/install.js`; the published script resolves a platform archive from a GitHub release, downloads it, verifies a SHA-256 sidecar, extracts it and installs the binary. Two properties are worth recording, neither a vulnerability claim:

- the checksum is fetched from the **same origin** as the artifact, so it covers corruption, not a compromised release origin;
- the base URL, repository and version are overridable via environment variables, so a redirected download is verified against a checksum from the same redirected location.
